# Spec: Architecture Lab

Status: **draft for review** · Scoped 2026-11-04 via `grill-me` (two rounds, Q1–Q18 all accepted) · Owner: Ella Etchandy

## Problem Statement

I am learning how segmentation CNNs work, and I want to choose a better model and preprocessing for mammogram mass segmentation without burning GPU hours on every candidate. Today the only signal I get is a Dice number at the end of a 20-epoch Colab run. I cannot see what each stage of the network does to a mammogram, why a particular mass was missed, how a candidate encoder (for example Mammo-CLIP's) encodes the same image differently, or what a model would cost in parameters, FLOPs, memory and time before I train it. Papers describe architectures in prose and tables, which does not build intuition. My classmates and anyone reading the repo have the same gap.

## Solution

A public, static web page, the **Architecture Lab**, generated by a CPU-only Python command. The command runs a small set of models over eight of my own mammograms (chosen to span good, mediocre and failed outcomes) under several preprocessing options, and records everything a reader needs to understand and compare them: tensor shapes, kernels, parameters, FLOPs, activation memory, latency, feature maps at every stage, squeeze-and-excite channel weights, receptive fields, saliency, predicted masks and Dice. The page presents this in five tabs:

1. **Anatomy**: the existing explainer, generalised so it can describe any loaded model (architecture map, convolution and pooling sandboxes, real kernels, parameter breakdown, layer table).
2. **Simulate**: pick model × preprocessing × image, then click any stage to see its feature maps, SE weights, receptive field and saliency for that image, with the prediction, ground truth and Dice.
3. **Compare**: two models, or two preprocessings of the same model, side by side on the same image and stage.
4. **Compute**: per-model and per-stage parameters, FLOPs, activation memory, input bytes and CPU latency, with a 256 / 512 / 1024 resolution slider for the quantities that scale analytically.
5. **Glossary**: the terms used across the page.

Everything is precomputed; the page is data plus a viewer. Anyone can regenerate it with their own checkpoint or images on a laptop in minutes.

## User Stories

1. As a student, I want to click any stage of the network and see what it did to a real mammogram, so that "feature map" stops being an abstraction.
2. As a student, I want to hover a cell in a deep feature map and see the patch of the input it can see, so that I understand receptive fields and why small masses vanish at the bottleneck.
3. As a student, I want to see the 2D convolution, pooling and activation operations with the model's real kernels, so that the arithmetic behind the network is concrete.
4. As a student, I want to see the squeeze-and-excite weights for a specific image, so that I understand what "the block turned channels up or down" means in practice.
5. As a student, I want to see which input pixels drove the predicted mask, so that I can tell what a model was looking at when it missed a mass.
6. As a student, I want each term on the page linked to a plain-language definition, so that I can read it without a textbook open.
7. As a researcher, I want to put two models side by side on the same image and stage, so that I can see how an ImageNet-pretrained encoder and a mammography-pretrained encoder represent the same tissue.
8. As a researcher, I want to switch the preprocessing under a fixed model, so that I can tell whether a Dice gain came from the filter or from training.
9. As a researcher, I want to apply a model to a preprocessing it was not trained on, so that I can test how brittle it is.
10. As a researcher, I want the same model shown at 256 and 512 input, so that I can see what resolution buys before I pay for a training run.
11. As a researcher, I want parameters, FLOPs, activation memory and latency per stage, so that I know where a model's cost concentrates and what to shrink.
12. As a researcher, I want those costs projected to 256, 512 and 1024 inputs, so that I can plan the resolution experiment with a compute budget in mind.
13. As a researcher, I want input bytes per image at each resolution and dtype reported, so that the dataset-packaging decision is grounded in numbers.
14. As a researcher, I want the eight sample images to include clear failures, so that the lab is diagnostic rather than a showcase.
15. As a researcher, I want a badge whenever a model's decoder is untrained, so that I never mistake a random mask for a prediction.
16. As a researcher, I want the lab's numbers labelled as illustrative and the experiment log kept as the only source of reported results, so that the two are never confused.
17. As a classmate, I want to open the lab from a public link with no installation, so that I can learn from it in a browser.
18. As a classmate, I want the page to work on my phone, so that I can read it anywhere.
19. As a member of the public, I want a documented one-line command that rebuilds the lab from my own checkpoint and images, so that I can evaluate my own model cheaply.
20. As a member of the public, I want the generator to run on CPU in minutes, so that evaluation does not require a GPU.
21. As a member of the public, I want the dataset and model licences and citations shown, so that I know what I may reuse.
22. As the instructor, I want the baseline notebook left untouched, so that the graded work remains exactly as submitted.
23. As a future maintainer, I want the data bundle small and committed, so that the page keeps working if the generator's dependencies rot.
24. As a future maintainer, I want the generator to refuse to write a bundle over its size budget, so that the repo never silently bloats.
25. As a future maintainer, I want the ground-truth masks built from mass polygons only, so that the lab and later experiments share one correct label definition.
26. As a future maintainer, I want the page to render correctly in light and dark themes, so that it matches the rest of the repo's pages.

## Implementation Decisions

**Models in the lineup**

- U-Net with EfficientNet-B0 encoder, trained on raw images (team checkpoint from Drive). Native preprocessing: raw.
- U-Net with EfficientNet-B0 encoder, trained on CLAHE + median images (team checkpoint). Native preprocessing: CLAHE + median.
- U-Net with Mammo-CLIP EfficientNet-B2 encoder. Encoder pretrained on mammograms; decoder randomly initialised. Marked "decoder untrained".
- U-Net with Mammo-CLIP EfficientNet-B5 encoder. Same treatment.
- Every model runs at 256 and 512 input. Latency is measured at both; FLOPs, activation memory and input bytes are additionally computed at 1024 from a trace with random input.

**Mammo-CLIP encoder loading** (facts verified from the Mammo-CLIP source)

- The published checkpoints use a vendored lukemelas EfficientNet, whose module names match the segmentation library's `efficientnet-b2` / `efficientnet-b5` encoders exactly. Loading is a prefix strip of `image_encoder.` from the checkpoint's `model` state dict; no renaming.
- The checkpoints are 1.3 to 1.5 GB each because they bundle a text model and optimizer state. The generator downloads each once, extracts the image encoder (8M / 28M parameters), and saves it as a small local file. Checkpoints and extracted encoders are never committed.
- Input convention for these encoders: grayscale replicated to 3 channels, per-image min–max to [0, 1], then `(x − 0.3089279) / 0.2505356` on every channel. Pretraining resolution was 1520 × 912 portrait; the lab runs 256 and 512 squares for comparability and records this mismatch.
- Licence CC BY-NC-SA 4.0; credit Ghosh et al. 2024 (arXiv 2405.12255) on the page and in the README.

**Preprocessing axis**

- `raw`: as stored (8-bit PNG).
- `clahe_median`: median filter size 3, then CLAHE clip 2.0, tile 8 × 8 (the baseline's exact recipe).
- `pca`: the baseline's per-image column PCA at 90 % variance (kept because it is in the reported results, even though it is a poor method).
- `breast_crop`: threshold, largest connected component, bounding box, then resize. A preview of roadmap step 2; no model was trained on it.
- Each trained model has a native preprocessing. The manifest records it; the page selects it by default and allows any pairing ("cross-apply").

**Sample images**

- Eight images from the baseline's test split, reproduced exactly (sorted filenames, 80/20 split, seed 42) using the per-sample metrics the team saved: two highest CLAHE Dice, two near the median, two with Dice 0 for every model, two with the smallest mass area that any model found.
- Raw and CLAHE versions are obtained from the team's Drive; the raw files come from the dataset archive. Downsampled copies, overlays and thumbnails are committed under the dataset's CC BY 4.0 licence with the TOMPEI-CMMD citation.

**Ground truth**

- Masks are rasterised from annotation polygons whose finding type is "mass" only. The baseline merged all finding types; this is the first place the corrected definition is used, and the baseline numbers will be re-run under it in the data-packaging experiment.

**What is recorded per model × preprocessing × image × resolution**

- Every leaf module: type, kernel size, stride, padding, groups, in/out shapes, parameters, multiply-accumulates (from shapes: output elements × input channels per group × kernel area for convolutions; elementwise counts for norms and activations), output tensor bytes.
- Per stage (encoder levels, decoder blocks, head): feature maps of the 16 highest-variance channels, each normalised and resized to at most 96 px, tiled into one PNG sprite; channel indices and per-channel mean, standard deviation and sparsity in the manifest.
- Squeeze-and-excite: the per-channel gate vector for every MBConv block (hook on the gate's sigmoid output).
- Receptive field per stage: computed analytically from the kernel, stride and padding chain, stored as the theoretical size and jump so the page can draw the input patch for any hovered cell.
- Saliency: Grad-CAM at the deepest encoder stage and at the stride-4 decoder block. Target scalar is the mean logit inside the ground-truth mass; when the model's predicted region does not overlap the ground truth, a second map targets the mean logit inside the predicted region. Stored as heatmap PNGs.
- Prediction: sigmoid map and thresholded mask as PNGs; Dice, IoU, predicted versus true mass area.
- Timing: median of five forward passes after two warm-ups, fixed thread count, per model and per stage, labelled with the machine (Apple-silicon CPU) and resolution.
- Analytic compute at 256 / 512 / 1024: parameters (constant), multiply-accumulates, activation bytes, input bytes per image for uint8 and float32.

**Data bundle and page**

- One JSON manifest plus PNG sprites, heatmaps, masks and thumbnails. Hard budget 25 MB; the generator refuses to write a bundle over budget.
- The page is a single HTML file with inline CSS and JavaScript, no framework, same theme tokens and conventions as the existing explainer, loading the manifest from a sibling file so it works from GitHub Pages, from a local file, and as a published artifact.
- The existing explainer's content becomes the Anatomy tab and is generalised to render any model in the manifest.
- The generator is a module runnable from the repo root with `--help`, taking the models, images, preprocessings and resolutions as arguments and a config file for the full default run.

**Honesty rules**

- Every number on the page is labelled illustrative; the experiment log remains the only source of reported results.
- Untrained decoders carry a visible badge wherever their prediction appears.
- Latency carries the hardware label everywhere it is shown.

## Testing Decisions

A good test checks external behaviour at a seam: given inputs, the outputs a reader or the page depends on. Tests do not inspect internal variables or exact pixel values of feature maps.

Seams, highest first:

1. **Generator end to end** (the preferred seam). Run the generator on a tiny configuration: one model with random weights, one synthetic image, one preprocessing, resolution 64. Assert that it writes a manifest that validates against the manifest schema, that every file the manifest references exists, that the bundle is under budget, and that the per-stage shapes match the traced model. Also assert that a configuration whose bundle would exceed the budget is refused.
2. **Pure functions** behind the generator, each a small unit test: mass-only mask rasterisation from a polygon list with mixed finding types; the multiply-accumulate counter against hand-computed values for a known convolution (for example the baseline's stem: 32 × 128 × 128 × 9 at 256 input); the receptive-field calculator against hand-computed values for a two-layer chain; the breast-crop on a synthetic image with known bounds; Dice and IoU on known masks; the Mammo-CLIP prefix-strip loader returning no missing and no unexpected keys when given a fabricated state dict with the right names.
3. **Page**: the inline script is syntax-checked and every element id the script references exists in the markup, using the same check already used for the explainer. No browser automation.

Prior art: there are no tests in the repository yet; this build adds a `tests/` directory and pytest to the development requirements. Tests run on CPU with no downloads.

## Out of Scope

- Training any model, including the Mammo-CLIP decoders. That is a separate experiment on the roadmap.
- Live inference in the browser.
- More than eight sample images, or images outside the baseline's test split.
- Findings other than masses.
- GPU measurements of any kind.
- nnU-Net, MedSAM / SAM and the lightweight encoders. They were discussed and can be added to the lineup later through the same generator.
- VersaMammo: its weights are no longer distributed.
- Any change to the baseline notebook.

## Further Notes

- Sequencing: build the generator and its tests first, run it on the baseline model alone, then add the Mammo-CLIP encoders, then build the page against the real bundle. The page's Anatomy tab is a refactor of the current explainer, not a rewrite.
- The eight raw sample images are the one external dependency that is not scriptable from this machine: they exist only inside the team's 966 MB dataset archive on Drive. They must be placed locally before the full run; the generator checks for them and names what is missing.
- Decoder channel widths and whether to freeze the encoder came up during scoping as a later experiment (overfitting risk of the 2.2 M-parameter decoder trained from 810 images). It is not part of this build but the Compute tab should make the decoder's share of cost obvious so that experiment is easy to motivate.
- Hosting: GitHub Pages from the `docs/` folder, which needs a one-time toggle in the repository settings by the owner.
